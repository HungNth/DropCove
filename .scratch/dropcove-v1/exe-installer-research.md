# DropCove x64 EXE installer research

## Recommendation

Use an **in-place conversion to an unpackaged C# WinUI 3 project**, publish a **win-x64 self-contained output folder with `dotnet publish`**, and wrap that folder with **NSIS**. This is the smallest policy-compliant CLI-first path to a conventional single-EXE installer. Do not re-scaffold the app: Microsoft documents un-packaging an existing WinUI app, and Microsoft's own self-contained C# WinUI sample keeps the normal WinUI project shape, `Package.appxmanifest`, `EnableMsixTooling`, and `WindowsPackageType=None` together ([unpackage a WinUI app](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app), [Microsoft sample `.csproj`](https://raw.githubusercontent.com/microsoft/WindowsAppSDK-Samples/main/Samples/SelfContainedDeployment/cs2/cs2.csproj)).

## Supported CLI build shape

The app project should contain these deployment properties (the existing project already has `SelfContained=true`, `RuntimeIdentifier=win-x64`, `PlatformTarget=x64`, and `EnableMsixTooling=true`; see [`src/DropCove.App/DropCove.csproj`](../../src/DropCove.App/DropCove.csproj)):

```xml
<WindowsPackageType>None</WindowsPackageType>
<WindowsAppSDKSelfContained>true</WindowsAppSDKSelfContained>
<SelfContained>true</SelfContained>
<RuntimeIdentifier>win-x64</RuntimeIdentifier>
```

- Microsoft defines `WindowsPackageType=None` as the C# WinUI switch for unpackaged distribution ([unpackage a WinUI app](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app)).
- `WindowsAppSDKSelfContained=true` copies the Windows App SDK dependencies into the output; a .NET app also needs normal .NET self-contained publishing (`SelfContained=true`) to carry the .NET runtime ([self-contained deployment](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps)).
- Publish the x64 RID using the documented .NET CLI form `dotnet publish -c Release -r win-x64 --self-contained true` ([.NET publishing overview](https://learn.microsoft.com/en-us/dotnet/core/deploying/)). The resulting publish directory—not a hand-selected subset—should be the input to the installer. Microsoft explicitly says unpackaged self-contained dependencies can be xcopy-deployed or included in a custom installer ([self-contained deployment](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps)).
- `PublishSingleFile` is **not required** for a single-EXE installer: Inno Setup produces the installer EXE while the installed application may remain a folder. If a single application EXE is later desired, Microsoft supports it only for unpackaged + self-contained WinUI 3 (Windows App SDK 1.5+) and it extracts dependencies at first launch; required properties include `WindowsPackageType=None`, `WindowsAppSDKSelfContained=true`, `SelfContained=true`, `EnableMsixTooling=true`, `IncludeAllContentForSelfExtract=true`, and `PublishSingleFile=true` ([single-file EXE requirements](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app#single-file-exe)).

## Runtime/bootstrap requirements

- For unpackaged apps, Windows App SDK initialization is required before using WinUI/other Windows App SDK APIs. `WindowsPackageType=None` enables the generated auto-initializer; an explicit `Bootstrap.Initialize` call is only for advanced cases such as custom error handling or selecting a different runtime ([runtime initialization](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/use-windows-app-sdk-run-time)).
- In the **self-contained** case, the app does not use the framework package/bootstrapper. With `WindowsAppSDKSelfContained=true`, `WindowsPackageType=None`, and an executable output, `WindowsAppSdkUndockedRegFreeWinRTInitialize` defaults to `true`; that automatic registration-free WinRT support is the required startup path ([self-contained deployment](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps), [deployment overview](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/deploy-overview)). Do not add an explicit bootstrapper call unless this default is deliberately disabled.
- Unpackaged WinUI deployment still requires the **Visual C++ Redistributable** on the target machine ([unpackaged deployment prerequisites](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/deploy-unpackaged-apps)). The .NET runtime itself is covered by `SelfContained=true`; the installer must still carry/install the appropriate x64 VC++ Redistributable or document it as a prerequisite.
- Keep the side-by-side application manifest with OS compatibility declarations; Microsoft calls this out for unpackaged apps ([runtime initialization, OS compatibility](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/use-windows-app-sdk-run-time)). DropCove already has [`app.manifest`](../../src/DropCove.App/app.manifest) with `supportedOS` and DPI settings.

## Inno Setup vs. WiX

| Tool | CLI and native-tool requirement | Commercial/licensing finding | Fit |
|---|---|---|---|
| **Inno Setup** | `ISCC.exe` compiles `.iss` scripts directly from the command line; its official feature list includes a single-EXE setup. The compiler invocation is a standalone installer-tool step rather than an MSBuild/native application build step ([compiler CLI](https://jrsoftware.org/ishelp/topic_compilercmdline.htm), [features](https://jrsoftware.org/isinfo.php)). | `LICENSE.TXT` expressly permits commercial use. The vendor requests commercial users purchase a perpetual commercial license; the vendor's FAQ says purchase is not strictly required and can wait until production ([license](https://jrsoftware.org/files/is/license.txt), [commercial license FAQ](https://jrsoftware.org/isorder.php)). | **Recommended minimum**: one short script, one compiler, one setup EXE, no extra native build toolchain. |
| **WiX** | Official WiX supports command-line builds with `dotnet build`/the `wix` .NET tool and requires the .NET SDK for that path; it can build MSI and Burn EXE bundles ([WiX usage](https://docs.firegiant.com/wix/using-wix/), [WiX quick start](https://docs.firegiant.com/quick-start/)). Building WiX itself from source is a different matter: the official repository lists Visual Studio and MSVC prerequisites ([WiX README](https://raw.githubusercontent.com/wixtoolset/wix/main/README.md)). | Source is MS-RL, but current official binary releases are subject to the Open Source Maintenance Fee agreement for revenue-generating users with annual gross revenue >= US$10,000; self-compiled binaries are outside that binary-release agreement ([WiX source license](https://raw.githubusercontent.com/wixtoolset/wix/main/LICENSE.TXT), [OSMF EULA](https://raw.githubusercontent.com/wixtoolset/wix/main/OSMFEULA.txt), [official WiX overview](https://docs.firegiant.com/wix/)). | Technically viable without MSVC when consuming the official .NET tool, but heavier authoring and an extra commercial-fee decision. Not the minimum path here. |

## Bottom line

Convert the existing packaged project in place rather than re-scaffolding. Set the two Windows App SDK properties above, publish the complete x64 self-contained folder with the documented .NET CLI, include the VC++ Redistributable prerequisite, and use NSIS's `makensis.exe` in the packaging step. Keep MSIX/Store work as a later distribution track; an unpackaged install has no package identity and is not an MSIX Store submission ([unpackaged WinUI limitations](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app)).
 
## NSIS finding (CLI-first commercial alternative)
 
**Recommendation: use NSIS instead of Inno Setup for this installer.** NSIS's official license page says its source, plug-ins, documentation, examples, headers, and graphics are under the zlib/libpng license (with bzip2 and LZMA module exceptions); the zlib/libpng text expressly grants use “for any purpose, including commercial applications,” subject to attribution/origin and notice-preservation conditions ([NSIS license](https://nsis.sourceforge.io/License)). This avoids the current Inno Setup compiler's “Non-commercial use only” conflict; Inno's separate license/FAQ describe commercial use and a requested commercial purchase ([Inno license](https://jrsoftware.org/files/is/license.txt), [Inno commercial FAQ](https://jrsoftware.org/isorder.php)).
 
- **Standalone CLI compiler / no VS or MSVC:** the official downloads publish a Windows setup and a portable `nsis-3.13.zip`; the official manual documents `makensis.exe myscript.nsi`, compiler switches, and generated-installer switches ([official downloads](https://nsis.sourceforge.io/Download), [compiler and installer command line](https://nsis.sourceforge.io/Docs/Chapter3.html)). The prebuilt package is the required toolchain step; using it does not require Visual Studio, MSVC Build Tools, standalone MSBuild, or XAML tooling. (Building NSIS itself from source is a separate, unnecessary path.)
- **Install/uninstall and complete publish output:** NSIS generates self-contained executable installers, supports uninstall generation via `WriteUninstaller`, and recursively embeds/copies a publish tree with `File /r`; its feature list explicitly includes install, uninstall, file/directory copying and executable execution ([features](https://nsis.sourceforge.io/Features), [`WriteUninstaller`](https://nsis.sourceforge.io/Reference/WriteUninstaller), [`File`](https://nsis.sourceforge.io/Reference/File)).
- **x64 and launch/close behavior:** use `$PROGRAMFILES64` for the x64 destination and `SetRegView 64` for 64-bit registry access ([`$PROGRAMFILES64`](https://nsis.sourceforge.io/Reference/$PROGRAMFILES64), [`SetRegView`](https://nsis.sourceforge.io/Reference/SetRegView)). `Exec`/`ExecShell` launch the installed DropCove executable ([`Exec`](https://nsis.sourceforge.io/Reference/Exec), [`ExecShell`](https://nsis.sourceforge.io/Reference/ExecShell)); before uninstall, `FindWindow` plus `SendMessage ... ${WM_CLOSE}` can request a normal application close, with `ExecWait` available where a process must finish before deletion ([`FindWindow`](https://nsis.sourceforge.io/Reference/FindWindow), [`SendMessage`](https://nsis.sourceforge.io/Reference/SendMessage), [`ExecWait`](https://nsis.sourceforge.io/Reference/ExecWait)). Request administrative installation with `RequestExecutionLevel admin` ([reference](https://nsis.sourceforge.io/Reference/RequestExecutionLevel)).
 
NSIS therefore satisfies the initial unpackaged `win-x64` self-contained publish wrapped in a conventional EXE installer, with a permissive commercial-use license and a portable standalone compiler. Keep the VC++ Redistributable prerequisite noted above; NSIS does not remove that WinUI runtime requirement.
