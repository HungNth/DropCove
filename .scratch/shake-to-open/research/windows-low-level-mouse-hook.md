# Windows low-level mouse hook — verified facts and implementation choice

## Official contracts

- `WH_MOUSE_LL` is a global-only hook. Its callback runs in the installing thread's context, which must have a message loop; the hook is not injected into the other process. [SetWindowsHookExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw), [LowLevelMouseProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc).
- For `nCode < 0`, pass directly to `CallNextHookEx`. For non-suppressing observation, continue the chain for every event. Mouse move and left-button down/up are supported callback messages. [LowLevelMouseProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc).
- `MSLLHOOKSTRUCT` provides per-monitor-aware screen coordinates, a message timestamp, and injection flags. `LLMHF_INJECTED` identifies injected input; `LLMHF_LOWER_IL_INJECTED` identifies lower-integrity injection. The documentation describes these flags but does **not** mandate filtering them for UIPI compliance. [MSLLHOOKSTRUCT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-msllhookstruct).
- Exceeding `LowLevelHooksTimeout` can silently remove the hook on Windows 7 and later, with no supported removal notification. The maximum timeout is 1000 ms on Windows 10 version 1709 and later. Microsoft recommends a dedicated hook thread that hands off work and returns immediately. No official 50-microsecond callback deadline or zero-risk guarantee exists. [LowLevelMouseProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc).
- `PostMessageW` posts asynchronously to an HWND's owning thread, is subject to UIPI, and can fail when the queue limit is reached. The system queue limit is 10,000 messages. Passing scalar signals avoids cross-thread pointer lifetime problems. [PostMessageW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-postmessagew).
- `PostThreadMessageW` targets a thread queue. Thread messages have no HWND and may be discarded by modal loops. A dedicated loop that explicitly handles these messages avoids that particular modal-loop problem; UI notifications should target a real HWND. [PostThreadMessageW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-postthreadmessagew).
- `DESKTOP_HOOKCONTROL` is the desktop access right required to establish hooks. Creating a desktop can supply a separate security descriptor; this does not establish that restricting it would isolate only Shake and leave every other desktop integration working. [Desktop rights](https://learn.microsoft.com/en-us/windows/win32/winstation/desktop-security-and-access-rights), [CreateDesktopW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-createdesktopw).

## DropCove implementation choice

Use one dedicated `dropcove-shake-hook` thread and its Win32 message loop. The callback copies scalar input into a preallocated bounded queue, schedules off-callback detection, and continues the chain. Detector results are posted to the Shelf HWND; Resident, Window, and Settings operations remain on Tauri's UI thread. Teardown unhooks and joins before releasing callback/receiver ownership.

Same-integrity injected input remains observable for accessibility and automated native smoke. Lower-integrity injected movement is ignored by product policy, not because the API mandates it. All live automated pointer checks must identify themselves as injected-input coverage; physical mouse polling rates and mixed-DPI hardware remain separate limits.

Installation failure is nonfatal and preserves desired settings for explicit Save retry. Settings application snapshots the actual runtime and joins hook changes with the existing atomic settings transaction. Testing must distinguish deterministic installation-error injection from native runtime failure handling and from an actual OS installation denial.
